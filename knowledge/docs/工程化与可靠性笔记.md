# 工程化与可靠性笔记（示例资料，可替换为你的真实笔记）

## Docker 容器化要点

- 分层缓存：依赖清单单独拷成一层，改业务代码不会触发依赖重装，构建时间从 8 分钟降到十几秒。
- 非 root 运行：容器里新建普通用户再启动进程，不要把服务跑在 root 下。
- 数据卷：容器是一次性的，数据库、日志、索引都要挂到卷上，否则容器一删就没了。
- 健康检查：必须留一个不带任何外部依赖的 `/health` 接口；注意它**不**该去检查外部依赖，否则外部一挂，容器就被判不健康、反复重启，把降级能力也弄没了。
- 优雅退出：用 `exec` 让应用进程直接成为 PID 1，停止信号才能传达到它，否则要等超时被强杀。

## CI 与离线测试

- 单元测试不能依赖 API Key 和网络，否则公共 CI 上跑不了，也容易泄露密钥。
- 把「需要真实模型」的评测与「纯逻辑」的测试分开：前者手动触发并花钱，后者每次提交都跑。

## 日志打点与耗时归因

- 每个环节都要记录开始、完成、异常与耗时，否则出现性能问题只能靠猜。
- 我真实吃过一次亏：链路里有 25 秒没人认领，加打点才发现是模型在生成一段根本没人使用的总结。
- 日志必须带可归因的操作名与上下文，只有一句「调用失败」等于没写日志。

## 重试、退避与超时

- 重试层数要唯一：SDK 层和业务层都配重试会**相乘**，3×3 变成 9 次请求。
- 指数退避加抖动：按固定间隔重试会让并发请求一起打过去，把刚缓过来的上游重新打垮（重试风暴）。
- 区分错误类型：上游过载（429/5xx/超时）值得长等，输出不合规（schema 校验失败）不该等——重新生成才有意义。
- 超时要按节点分层：长文本生成和短结构化输出共用一个阈值，要么误杀慢节点，要么让快节点白等。

## 评测集设计

- 指标要能区分「内容质量」和「基础设施故障」，混在一起会误导排查方向。
- 失败用例的耗时如果都撞同一个整数特征值（例如都是 205 秒），多半是超时阈值或重试门槛的问题，不是模型退化。
- 评测结果要如实写出失败项与根因，写一个含糊的「全部通过」反而没有说服力。
