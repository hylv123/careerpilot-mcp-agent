## 第四轮（2026-11-03）：换模型 + 四处修复后重跑

| | 11-03 |
| --- | :---: |
| 通过率 | 20/20 |
| 运行异常 | 0 例 |

这一轮同时换了两样东西：模型（`deepseek-flash`，并显式关闭思考模式）和四处代码修复（保存结果可观测、日志初始化移出入口、sqlite 连接统一关闭、ACK 失败不再杀进程）。

所以**耗时从 19.7 分钟降到 2.9 分钟不能全归因于代码**——主因是模型与思考模式的差异。四轮合起来看：17/20 → 20/20 → 19/20 → 20/20，两次失败（ReadTimeout、SSL EOF）都是环境/链路问题，不是生成质量。

> 注意：这一轮指标已经饱和（四项全 20/20），它的价值是"结构性回归没坏"，不能用来说明质量提升。

## 10-16 那两处改动（至今保留）

1. **读超时从"全局 60 秒"改成"分节点 60 / 90 / 120 / 150 / 180 秒"**
   一次分析要打 5~7 次模型请求，超时限制的是**单次请求**。共用同一阈值时，短节点白等、长节点（`report` 实测 37 秒）被误杀。

2. **消除最后一轮 agent 空转**
   `agent_node` 原本没有 system 指令，模型不知道自己该干什么，就在末尾写一段几百字总结——而这段总结没有任何消费者。现在轮次达上限直接跳过该次调用，并注入指令要求"信息足够时只输出 finish"。实测该步从 **58.3 秒降到 7.6 秒**。

## 一个失败用例的判读方式

10-17 那轮唯一失败的 `real-09` 与生成质量无关：它在第一步就撞上 `[SSL: UNEXPECTED_EOF_WHILE_READING]`，上游 TLS 连接被意外掐断，重试 3 次都是同一个网络故障。

判断依据是三个特征同时出现：

- 耗时 51 秒（明显短于正常用例）
- `error` 字段为空、报告文本为空
- 重试次数用尽

这正是"链路没跑完"，而不是"跑完了但内容不对"。评测把这两类分开记录，所以这个结论站得住。
