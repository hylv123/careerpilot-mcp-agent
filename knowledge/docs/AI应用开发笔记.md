# AI 应用开发笔记（示例资料，可替换为你的真实笔记）

## Prompt 工程

- 结构化输出优先：让模型按 Pydantic schema 返回，比让它输出一段自然语言再正则去抓要稳得多。
- 指令要写清"不做什么"（不要编造、不要输出解释性文字），只写"要做什么"时模型会自由发挥。
- 少样本示例对格式稳定性帮助很大，但示例本身会占 token，需要权衡。
- 长 prompt 不等于好 prompt：把无关上下文塞进去反而会稀释重点。

## 工具调用与 Function Calling

- 把能力做成独立工具（查询、写入、生成文档），由模型决定是否调用，而不是把逻辑全写死在脚本里。
- 工具描述写得越具体，模型选得越准；描述含糊会导致它乱调或根本不调。
- 要给工具调用设上限：模型可能在多轮之间反复调用，既烧钱又拖慢响应。

## 检索增强生成（RAG）

- 先检索再生成，回答必须能指向原文片段，否则无法验证真伪。
- 切块策略直接影响效果：过短丢上下文，过长引入噪声；中文场景 300 字左右、overlap 约 50 字较稳。
- 只按"返回了几条"判断检索质量是不够的——相关度不足时要改写查询并补充检索。
- 距离阈值要结合自己的知识库和 embedding 模型实测校准，不能照抄别人的数值。

## 模型选型与成本

- 不同节点可以用不同档次的模型：简单抽取用快的，长文本生成用稳的。
- 一次完整调用往往是多次请求的串联，算成本要按"次数 × 单次"而不是按"一次任务"。
- 记录每次调用的输入输出 token，才知道钱花在哪一步。

## 效果评测

- 不能只看最终回答顺不顺眼，要单独测检索环节：给定查询，应该召回的片段有没有被召回。
- 人工标注一批"标准答案"是绕不开的工作，没有标注集就只能靠主观感觉。
- 指标要分开看：召回率看"有没有找到"，精确率看"找到的里有多少是有用的"。
